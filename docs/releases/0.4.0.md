TESK 0.4.0 deploys [TESK API 2.0.0](https://github.com/elixir-cloud-aai/tesk-api/releases/tag/v2.0.0), which implements TES 1.1, and the taskmaster and filer of [tesk-core 0.12.0](https://github.com/elixir-cloud-aai/tesk-core/releases/tag/v0.12.0) by default. It switches the API's Deployment to the update strategy `Recreate`, so that one `helm upgrade` brings the new API and taskmaster in the order they need, and refuses a taskmaster 0.12.0 or later with an older API. New values let browser apps call the API (CORS origins), let tesk-api accept the tokens of allow-listed service clients, and set the security contexts of the hardened filer pods. Releases of chart 0.3.0 are upgraded in place; read the [upgrade notes](https://github.com/elixir-cloud-aai/TESK/blob/v0.4.0/docs/upgrading.md#040) first, especially if your values pin image tags or your cluster refuses pods with the `RuntimeDefault` seccomp profile. On OpenShift (e.g., Rahti), keep `tesk.podSecurityContext.runAsUser: null` (OpenShift sets the user of pods), and where the cluster also rejects `RuntimeDefault` and sets its own seccomp profile, set `tesk.podSecurityContext.seccompProfile: null` and the new `tesk.filer.podSecurityContext: {runAsNonRoot: true}`.

## Breaking changes

- Default images tesk-api 2.0.0 and taskmaster and filer 0.12.0: the API implements TES 1.1 (the chart's service info reports `type.version` 1.1.0 from tesk-api 2.0.0 on), runs on Java 21 and Spring Boot 4, and changes some answers to clients (e.g., at most 256 tasks from `GET /tasks` without `page_size`, the states `CANCELING` and `PREEMPTED`, the API description at `/v3/api-docs`); the installation fails if the values pin a tesk-api before 2.0.0 with the taskmaster 0.12.0 or later, which would report wrong task states; see also the upgrade notes of tesk-api and tesk-core (#308, #309)
- Filer pods of taskmaster 0.12.0 run non-root, with the `RuntimeDefault` seccomp profile, no privilege escalation or capabilities and a read-only root filesystem; clusters that refuse `RuntimeDefault` need the new values `tesk.filer.podSecurityContext` and `tesk.filer.securityContext` (e.g., `tesk.filer.podSecurityContext: {runAsNonRoot: true}`) (#308, #309)
- The API's Deployment uses the update strategy `Recreate` by default (`tesk.strategy`), so the API is down for about a minute on every rollout; releases upgraded with server-side apply (e.g., Flux, Argo CD) need a one-time `kubectl patch` of the strategy, and `RollingUpdate` stays available for two-step upgrades (#305, #306)
- The FTP secret is created and passed on to tesk-api only if `ftp.username` or `ftp.password` is set; `helm upgrade` deletes the empty secret of releases without FTP credentials, so move credentials put into the secret by hand into the values first (#294, #298)

## Features

- `tesk.cors.allowedOrigins` lets browser apps of the listed origins call the API (tesk-api 2.0.0 or later); the schema refuses origins that tesk-api refuses at startup (#307, #310)
- `auth.tokenClients` lets tesk-api accept the access tokens of allow-listed clients, e.g., of a gateway that calls TESK with the client credentials grant (tesk-api 2.0.0 or later); the chart fails on incomplete settings instead of starting the API with them (#296, #299)
- `tests/smoke/deployment.sh` checks a deployed instance from outside: service info, access control, and a task that completes and one that is cancelled (#293, #297)
- From tesk-api 2.0.0 on, the chart's service info lists `tesResources_backend_parameters: []` (TES 1.1): TESK supports no backend parameters (#289, #314)

## Security

- With an FTP secret, the filer jobs of taskmaster 0.12.0 reference it (`TESK_FTP_SECRET_NAME`) instead of holding the FTP credentials as values (#308, #309)

## Documentation

- Deployment on clusters that set their own seccomp profile (`tesk.podSecurityContext.seccompProfile: null`) (#292, #295)
- The docs of tesk-api 2.0.0 and tesk-core 0.12.0 are pulled into the site (#308, #309)
